# 课件渲染架构评估与改进建议

状态：**2026-09-25 当前检出源码的静态审查 + 目标设计建议**。学生端和 Core 当前检出与根仓锁定指针不一致，尚未做教师/学生 Windows 实机联调。审查包含已落地的 `packages/course-format`、学生 UI 归位和教室 Hub 首轮实现；下文单独指出尚未接入当前课堂播放器的能力。课件字段和 SDK 的现状见[课件格式与 SDK](/reference/course-format-sdk)，迁移进度见[目标架构迁移状态](/status/migration)。

页面编码规范、可扩展组件库与插件机制的专项方案见[课件内容规范、插件与组件库设计](/architecture/course-content-extensions)。

## 结论

现有职责划分基本合理：教师服务托管课程文件和课堂状态，Core 提供浏览器加载与播放，教师页面、学生页面和导出预览复用同一渲染引擎；PDF 也有独立播放分支。共享 `course-format` 已提供 ZIP/manifest 校验、版本规则和内容 hash，教师服务扫描与中继 Hub 发布已接入。当前播放器仍用自己的弱校验和全局执行环境，加载/释放也没有按“一个课程实例”管理。下一步应让播放器接入共享格式库，建立隔离环境与明确的生命周期。

## 当前渲染链路

```mermaid
flowchart LR
  F[教师电脑课程目录] --> CF[共享 course-format 校验]
  CF --> H[教师服务<br/>扫描目录、提供目录和静态文件]
  H --> T[教师页面]
  H --> S[学生页面]
  T --> E[Core 浏览器引擎]
  S --> E
  E --> Z[ZIP 解包与资源 Blob URL]
  Z --> C[Babel 编译 TSX / 执行模块]
  C --> R[React 课件舞台]
  H --> P[Socket.IO 课程和页码状态]
  P --> T
  P --> S
  H --> X[导出预览页]
  X --> E
```

1. 当前教师服务扫描 `.lume`、PDF 和脚本文件；ZIP `.lume` 用共享 `course-format` 校验，损坏包进入目录结果的 `invalid` 列表。选课后服务端广播课程 ID，教师、学生页面分别从 `/courses/...` 获取文件并调用 `engine.loadCourse`。证据：`repos/teacher/server/src/courses.js:8,50-54,66-74,102-133`、`repos/teacher/server/src/socket.js:358-393`、`repos/teacher/shared/teacher-shell/src/app.tsx:1042-1075`、`repos/student/ui/classroom/src/classroom-app.js:191-212,330-339`。
2. 当前播放器的 ZIP 分支在浏览器完整下载文件，用 JSZip 解包，生成资源 Blob URL，逐页用 Babel Standalone 编译 TSX，再以 `new Function` 执行并生成 React 元素；随后加载依赖脚本并建立课程上下文。它没有调用共享 `course-format`。证据：`repos/teacher/core/src/browser/engine/runtime/app.tsx:87-160,250-343,476-525`。
3. 新教室 Hub 的中继发布链路已经用共享格式库校验上传包并核对 `courseHash`；教师会话代理完成暂存和发布。但当前教师/学生课堂页面还未改为按该 hash 从 Hub 加载隔离播放器，不能把 Hub 的门禁等同于旧课堂选课流程的端到端可播放性保证。证据：`apps/classroom-hub/src/routes.js:45-112`、`apps/teacher/session-agent/src/agent.js:1189-1294`。
4. `CourseStage` 复用 `SyncClassroom` 播放舞台；PDF 用 pdf.js 将页面画到 Canvas；导出预览也调用同一 `loadCourse`，但使用一套禁用部分交互能力的上下文。证据：`repos/teacher/core/src/browser/engine/runtime/app.tsx:346-429,458-474,528-563,597-695`、`repos/teacher/shared/public/export-preview.html:548-565`。

这里的“复用引擎”是浏览器代码复用，并非课件在教师端编译一次后分发给学生。各客户端仍独立下载、解包、编译和执行。Core 的 `CourseStage` 同时包含播放、同步变量、标注、投票及部分教师工具栏；它还不是纯粹的渲染核心。

## 合理之处

| 设计 | 评价 |
| --- | --- |
| 课程文件与课堂状态分开 | 文件走 HTTP、翻页走 Socket.IO，符合两种数据不同的更新频率；目标架构可继续使用。 |
| 教师、学生和导出预览复用 Core | 减少三套播放器分叉；需要通过相同版本的引擎和格式契约保证结果一致。 |
| ZIP 包带 manifest 与资源目录 | 共享格式库已提供 schema、路径/大小限制和内容 hash；当前浏览器播放器仍需接入。 |
| PDF 单独适配为页序列 | 可以沿用同一课堂页码模型；PDF 缓存和画布尺寸仍需优化。 |

## 架构问题与证据

| 优先级 | 问题 | 影响与源码证据 |
| --- | --- | --- |
| P0 | 课件代码没有隔离边界 | `new Function` 在课堂页面执行，能访问 `window`、DOM、Socket 和页面上可见的原生桥；`require` 白名单只限制 import 名称，不能限制全局访问。第三方依赖又以 `<script>` 注入同一页面。`app.tsx:127-160,476-506,585`；`resource-loader.tsx:6-53`。将来即便换 Electron 壳，也必须独立限制课件 origin、进程和 IPC 能力。 |
| P1 | 播放器未接入共享格式库，发布门禁不覆盖代码可执行性 | `course-format` 已在教师目录扫描和中继 Hub 上传中校验 manifest、ZIP 路径/大小/压缩比；但浏览器播放器仍用本地 `validateLumeManifest`，只检查 format、entryMode 和页面文件，无法保证直接收到的包遵循同一约束。服务端校验也不编译每页 TSX，语法/运行错误仍可能在全班选课后各自暴露。`packages/course-format/src/manifest.js:70-159`；`repos/teacher/server/src/courses.js:50-54,102-133`；`apps/classroom-hub/src/routes.js:45-112`；Core `app.tsx:176-190,258-320`。 |
| P1 | 加载顺序、并发与资源生命周期不完整 | 页面模块先编译和执行，`dependencies` 随后才加载；模块顶层若直接用依赖全局变量会失败。开始加载新包时先撤销上一包 Blob URL；错误路径没有统一的 finally 清理。教师和学生端的异步 `loadCourse` 未见请求代次或取消逻辑，快速切课可能使旧结果回写新课堂。Core `app.tsx:35-45,250-343,476-525`；教师 `repos/teacher/shared/teacher-shell/src/app.tsx:1042-1075`；学生 `repos/student/ui/classroom/src/classroom-app.js:191-212,330-339`。 |
| P1 | 全局可变上下文跨课程共享 | `window.CourseData`、`window.CourseGlobalContext` 和 Object URL 列表挂在同一个页面全局；课件模块执行时上下文建立于之后，旧值可能仍可见。课程卸载并不等于脚本、副作用、事件监听与计时器被撤销。`app.tsx:35-45,127-160,276-343,523-525`。这是从实现推导的风险，需用切课与副作用测试确认具体表现。 |
| P1 | 资源依赖不具备可复现性 | 加载器在本地脚本失败时回退第三方 CDN，且课程可声明任意 `publicSrc`；失败结果没有被依赖加载循环作为硬错误处理。不同教室网络可能播放不同版本或缺失依赖。`resource-loader.tsx:6-53`；`app.tsx:490-507`。 |
| P2 | 资源与布局成本由每个客户端重复承担 | 每台学生机完整下载 ZIP、解包全部 assets、编译所有页面；资源 URL 一次性创建。PDF 文档 Promise 按 URL 缓存在全局 Map，当前未见淘汰；Canvas 按固定 1280×720 目标与设备像素比渲染。大课件和高 DPI 设备的内存、首屏时间需测量。`app.tsx:87-110,258-343,346-395`。 |
| P2 | 播放、课堂协议和导出模式仍交织 | `CourseStage` 包着含标注、同步、工具栏的 `SyncClassroom`；导出预览用禁用能力的假上下文，无法证明互动页的导出内容等同课堂播放。`sync-classroom.tsx:80-155,640-685`；`app.tsx:458-474,597-665`。 |

## 建议的目标边界

```mermaid
flowchart LR
  ED[新编辑器] -->|同一格式库| CF[course-format<br/>schema、校验、迁移]
  ED -->|预览| PP[隔离播放器]
  T[教师应用] -->|导入和发布| CF
  CF -->|已校验内容 hash| HUB[Classroom Hub<br/>课程快照与静态资源]
  HUB -->|资源| PP
  HUB -->|版本化状态| CP[classroom-protocol]
  CP --> PP
  PP -->|受限消息| CAP[能力代理<br/>互动、资源、摄像头申请]
  CAP --> HUB
```

1. **把现有 `course-format` 接入全部入口。** 共享库已定义 schemaVersion、路径/大小限制、ZIP 读写和内容 hash；教师扫描、迁移脚本、会话代理与 Hub 已接入。下一步让浏览器播放器和新编辑器复用同一校验器，并补充明确的 runtimeVersion 兼容矩阵、依赖完整性与导出能力声明。旧脚本继续走显式迁移入口。
2. **`course-runtime` 拆为播放器与宿主适配器。** 先定义 `prepare(courseBlob, runtimeVersion, signal) → preparedCourse`、`mount(container, context) → dispose()` 之类的生命周期契约；每个课程实例自己持有 Blob URL、脚本/Worker、监听器和缓存。`prepare` 完成所有版本、依赖与页面检查后才能替换正在播放的课程。加载失败保持上一可用版本并显示可诊断错误。
3. **课件在独立信任边界执行。** 优先评估声明式组件/受控交互模型；若继续支持任意 TSX/JavaScript，使用隔离 origin 的 iframe/独立 WebView 或等效进程隔离，配严格 CSP、资源来源限制和版本化 `postMessage` 能力 API。宿主校验消息来源、课件身份和操作权限；课件不能直接访问教师/学生页面、Socket 或原生桥。React 组件不能跨隔离边界直接共享，因此迁移前应先做包含 SDK、图像、视频、互动的可运行原型。
4. **发布不可变课件快照。** 教师端或 Hub 校验通过后按 `courseHash + runtimeVersion` 发布；学生按 hash 下载、校验并缓存。课堂状态引用明确版本，教师修改文件不改变正在播放的内容。中继模式按[教师端与中继设计](/architecture/teacher-cross-platform-relay)的发布快照落地。
5. **课堂状态与课件状态分层。** 页码、当前课程版本由 Hub 唯一持有；课件内部临时状态经受控 SDK 同步。`CourseStage` 只负责版式、缩放和播放器容器；标注、投票、监看、教师工具栏归宿主 UI 或独立课堂插件。导出应声明可支持的页面能力，并用同一 `preparedCourse` 做静态快照。

## 分阶段改造与验收

| 阶段 | 最小交付 | 验收 |
| --- | --- | --- |
| 1. 固定现状 | 锁定教师/学生/Core 版本；建立 ZIP、PDF、互动、资源依赖样本；记录三端首屏、内存与切课行为 | 同一锁定版本可在 Windows 双机复现播放、翻页和导出，记录已知差异。 |
| 2. 格式与发布门禁 | 将已实现的 `course-format` 接入浏览器播放器和编辑器；补 runtimeVersion 兼容矩阵、依赖完整性与每页编译检查 | 教师扫描、Hub 发布、浏览器播放对同一包给出一致结果；坏包和无法编译的页在切换前被拒绝。 |
| 3. 生命周期与可靠性 | 课程实例、AbortSignal/代次、依赖先加载、失败回滚、统一 dispose、PDF 缓存上限 | 快速切课、断网、缺依赖与失败重试不回写旧结果、不泄漏 URL/监听器。 |
| 4. 隔离播放器 | 隔离环境与最小 SDK 消息协议；逐步迁移页组件 | 课件无法调用宿主 DOM、Socket 或原生能力；既有互动样本在授权能力内运行。 |
| 5. 性能与一致性 | 预编译或按页编译、按需资源解包、hash 缓存、导出能力声明 | 教师/学生/预览渲染结果在固定样本上可比对，较大课件的加载与内存有预算。 |

上述验收是后续实施门槛；第 2 阶段已有共享格式库与部分服务端接入，其余仍待完成。短期最应先完成播放器接入与第 3 阶段的生命周期改造，因为它们直接决定新编辑器产物能否稳定在教师、学生和中继模式播放。
